# 自定义麻将 · 可行性分析（GLM）

> 2026-09-04 · 开发前技术评估，结论支撑[需求文档](./需求文档.md)的技术选型

## 一、总体结论

**可行，复杂度中等。** 简化麻将（120 张、仅 3 番种、禁吃），所有难点均有成熟方案。最大风险不在算法，而在**规则歧义**与**两类结算时点**的正确建模。

## 二、模块难度评估

| 模块 | 难度 | 分析 |
|---|---|---|
| 胡牌/听牌判定 | 中 | 经典递归拆解（4 面子 + 1 将），成熟算法多。需先剔除发财再判定；中/白可入型，让字牌也参与组合枚举 |
| 双向牌墙 | 低 | 正向摸牌 / 墙尾补牌（发财补摸、杠后补摸）共享同一数组，只需两个指针 |
| 宝牌流程 | 低 | 摸到发财 → 亮牌 → 墙尾补摸 → 可能递归。注意起手 13 张中摸到发财也要即时补摸 |
| 报嘴状态机 | 中 | 锁死后的交互约束是 UI 重点：禁碰杠、摸啥打啥、摸到胡张**必须胡**（UI 要禁用"过"按钮）。状态转移本身简单 |
| 计分系统 | 中 | **两类结算时点**是本项目最易出错处：补杠即时付 vs 暗/明杠挂账终局付 vs 荒庄豁免。建议用「挂账队列 + 结算事件」建模，而非散落各处的加减分 |
| 番数计算 | 低 | 3 番种纯叠加，无复杂的上限/重复判定 |
| AI | 中 | 向听数评估 + 简单启发式即可达到"可玩"水平；报嘴决策（何时锁死）是唯一策略亮点 |

## 三、关键设计决策

1. **规则引擎与 UI 分离**：engine 为纯函数（无 DOM），Node 内置 test runner 直接单测。规则文档「结算示例」6 个场景必须全部转为测试用例。
2. **发财不进手牌数组**：单独 faCount 字段。胡牌判定、点炮资格（faCount ≥ 1）、番数全部围绕它。
3. **计分统一走账本**：`{即时分, 挂账分[]}`，终局/荒庄时分别清账，天然满足「荒庄暗杠明杠不结」。
4. **状态机显式化**：DEALING / TURN / BAO_DRAW / ACTION / CLAIM / SETTLE，报嘴约束在状态机层强制，不依赖 UI 自觉。

## 四、风险清单

| 风险 | 影响 | 缓解 |
|---|---|---|
| 规则歧义（已识别 10 条，见需求文档第五节） | 高 | 逐条给默认值，用户确认后锁死 |
| 摸到发财后的手牌数不变 | 中 | 补摸逻辑与普通摸牌统一入口，起手阶段也要走宝牌流程 |
| 报嘴 + 宝牌补摸交互（补摸张可胡必须胡、不可胡必须打） | 中 | 在 BAO_DRAW 状态单独分支处理，单测覆盖 |
| 同一弃牌竞争只认起牌顺序中的第一家 | 低 | CLAIM 阶段按本局起牌顺序取第一个非“过”声明 |
| 递归补财导致墙尾耗尽 | 低 | 墙尾与正向共享余量，摸尽即荒庄判定 |

## 五、工作量估计

- M1 规则引擎 + 单测：核心工作量，约 60% 精力
- M2 可玩原型（热座式）：UI 从简，先保证状态机跑通
- M3 AI 接入：启发式策略，含报嘴决策
- M4 打磨：动画、结算面板、可选音效
