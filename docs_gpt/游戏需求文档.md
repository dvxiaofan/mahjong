# 自定义麻将游戏需求文档（草案）

- **文档状态**：需求分析草案 v0.1
- **日期**：2026-09-04
- **规则依据**：上级目录《自定义麻将规则.md》（定稿）
- **目标**：把约定麻将规则实现为可玩的数字麻将，先完成本地单机 MVP，再视需要扩展联网。

---

## 1. 可行性结论

本玩法可以开发成游戏，规则层面可实现。最适合的技术路线是：

1. 先做一个浏览器端本地单机版：1名玩家 + 3名 AI；
2. 将洗牌、发牌、摸牌、发财补牌、鸣牌、听牌判断、报嘴、胡牌和结算写成独立的纯规则引擎；
3. UI 只负责展示状态和提交动作，不直接计算规则；
4. 规则引擎稳定后，再增加联网房间和服务器权威校验。

难点不在普通麻将牌型，而在以下自定义机制：

- 发财从手牌中分离，并从墙尾补牌；
- 三家通碰，需要处理弃牌响应和冲突；
- 报嘴后锁定听口，且摸到胡牌张必须胡；
- 明杠、补杠、暗杠的不同结算时机；
- 荒庄时所有杠分作废，已即时支付的补杠分退还；
- 一炮多响及同一弃牌的竞争按本局起牌顺序处理，谁先起牌谁优先。

这些机制适合用明确的有限状态机实现，不建议把规则散落在界面代码中。

---

## 2. 建议的产品分期

### 2.1 MVP：本地单机版

**目标**：能完整打一局，并严格按定稿规则结算。

- 运行方式：浏览器本地运行；
- 玩家：1名人类玩家 + 3名 AI；
- AI：先使用可解释的规则/启发式策略，不追求高水平；
- 存储：本地保存设置和最近牌局，可选保存回放；
- 暂不包含：账号、联网匹配、支付、排行榜、广告、社交系统。

### 2.2 第二阶段：本地体验完善

- 更完整的 AI 策略；
- 动画、音效、提示和移动端适配；
- 牌局回放和逐步复盘；
- 自定义房规开关；
- 更详细的得分和杠分流水。

### 2.3 第三阶段：联网版

- 创建/加入房间；
- 服务器权威洗牌和规则校验；
- WebSocket 实时同步；
- 掉线重连和托管；
- 房间密码、观战、战绩等功能。

联网版不是简单地把本地版加一个网络层，需要单独设计服务器状态、并发动作和作弊防护。

## 3. 已确认的规则模型

### 3.1 牌库

按每种牌 4 张计算，共 120 张：

- 万、筒、条：108 张；
- 红中、白板、发财：12 张；
- 无风牌、无花牌。

红中、白板为普通牌：可以碰、明杠、暗杠、进入牌型，不加番。
发财为特殊宝牌：

- 起手或自己摸到后，亮牌放在手牌旁；
- 每张发财 +1 番；
- 不碰、不杠、不参与牌型；
- 从墙尾（起牌顺序的反方向）补摸一张，保持正常手牌数量；
- 四张发财作为四张独立宝牌保留，不算杠。

### 3.2 鸣牌和杠

- 吃：禁止；
- 碰：上家、下家、对家三家都可以碰；
- 明杠：暗藏三张，别人打出第四张；
- 补杠：已有碰牌，之后自己摸到第四张；
- 暗杠：四张均由自己起牌或摸到；
- 发财不能参与任何杠；
- 无抢杠胡；
- 补杠即时结算，明杠和暗杠终局结算；
- 荒庄时所有杠分作废，已即时支付的补杠分退还。

### 3.3 胡牌和番种

- 胡牌结构：标准 4 面子 + 1 将；
- 碰出的面子计入牌型；
- 碰碰胡 +1 番；
- 清一色 +1 番；
- 发财每张 +1 番；
- 无起胡番要求；
- 无发财只能自摸；
- 至少 1 张发财才可以点炮；
- 杠后补牌胡牌算自摸，当前没有额外“杠上开花”番。

### 3.4 报嘴

- 有至少 3 张发财且当前听牌时，可以选择报嘴；
- ≥3张发财未报嘴时可以自摸，但不能点炮；
- 不报嘴不会失去继续摸打、碰杠和换听的资格；
- 报嘴后听口锁定；
- 报嘴后不能换听、碰或杠；
- 非胡牌摸牌必须原张打出；
- 摸到胡牌张必须胡；
- 报嘴后摸到发财，照常亮牌并补牌，补牌成胡时胡牌。

### 3.5 结算

- 自摸：三家各付 `1 + 番数`；
- 点炮：点炮者付 `1 + 番数`；
- 补杠：被碰者即时付 1 分；
- 暗杠：终局三家各付 1 分；
- 明杠：终局点杠者付 1 分；
- 一炮多响及同一弃牌竞争：按本局起牌顺序，谁先起牌谁优先，只认第一家；
- 荒庄：平局，所有杠分作废，已即时支付的补杠分退还。

## 4. 推荐技术方案

### 4.1 前端

- TypeScript；
- React + Vite；
- CSS 或轻量组件方案；
- 响应式布局，优先支持桌面浏览器，兼顾手机横屏。

### 4.2 规则引擎

规则引擎应是独立 TypeScript 模块，不依赖 React 或浏览器 API：

- 输入：当前状态 + 玩家动作；
- 输出：新状态 + 事件列表 + 可用动作；
- 使用确定性随机种子，便于测试和复盘；
- 所有动作先经过合法性校验；
- UI 不允许直接修改牌墙、手牌或分数。

### 4.3 数据结构建议

```text
GameState
├── players[4]
│   ├── concealedTiles
│   ├── exposedMelds
│   ├── fortuneCount
│   ├── mouthDeclared
│   ├── lockedWaits
│   ├── gangRecords
│   └── score
├── wall
│   ├── drawIndex
│   ├── replacementIndex
│   └── remainingCount
├── discards[4]
├── currentSeat
├── phase
├── pendingDiscard
├── pendingClaims
├── dealerSeat
└── eventLog
```

推荐将发财数量单独建模为 `fortuneCount`，不要把发财混入普通手牌数组。

### 4.4 动作类型建议

```text
DRAW
DISCARD
PASS
PONG
CONCEALED_KONG
EXPOSED_KONG
SUPPLEMENT_KONG
DECLARE_MOUTH
WIN_SELF_DRAW
WIN_DISCARD
```

发财的处理可以作为摸牌后的自动事件：

```text
DRAW -> DRAW_FORTUNE -> MOVE_FORTUNE_ASIDE -> REPLACEMENT_DRAW
```

## 5. 牌局状态机

建议至少包含以下状态：

1. `DEALING`：洗牌、发牌、处理起手发财补牌；
2. `READY`：确定庄家和起手顺序；
3. `DRAWING`：当前玩家从正常端或补牌端摸牌；
4. `FORTUNE_REPLACEMENT`：处理发财和补牌链；
5. `SELF_ACTION`：自摸、暗杠、补杠、报嘴或出牌；
6. `DISCARD_RESPONSE`：其他玩家对弃牌进行胡、碰、明杠或放弃；
7. `RESOLVE_CLAIM`：按优先级及座位顺序处理竞争动作；
8. `WIN_SETTLEMENT`：胡牌结算；
9. `DRAW_SETTLEMENT`：荒庄处理；
10. `ROUND_END`：确定下一局起手者。

报嘴玩家需要额外约束：

- 不生成碰、杠和换听动作；
- 自摸非胡牌时只能生成“原牌出牌”；
- 对符合听口的自摸胡张生成“必须胡”动作；点炮生成“胡/过”动作；
- 报嘴后摸到发财时，先完成发财补牌，再判断补牌是否胡。

## 6. AI 设计

MVP 的 AI 可以分三层：

1. **合法性层**：永远不执行非法动作；
2. **成牌层**：计算向听数、可进牌和基本番数；
3. **风险层**：根据其他玩家的碰牌、报嘴和弃牌，减少危险出牌。

第一版不必实现复杂机器学习。建议先实现：

- 优先保留有效搭子；
- 优先完成清一色或碰碰胡倾向；
- 有 3 张发财且听牌时自动报嘴；
- 报嘴后严格摸打；
- 能胡时按规则自动胡；
- 碰、杠、明杠按简单收益策略选择。

AI 的手牌选择必须调用同一套规则引擎，不能另写一套会产生不一致的胡牌判断。

## 7. UI 需求

### 7.1 牌桌

- 显示自己的手牌、发财区、碰牌和杠牌；
- 显示三名对手的座位、剩余手牌数量、发财数量和已报嘴状态；
- 显示四家的弃牌区；
- 显示牌墙剩余数量；
- 清楚标示当前行动玩家。

### 7.2 操作

- 摸牌、出牌；
- 可用动作按钮：胡、碰、杠、暗杠、报嘴、过；
- 报嘴时展示当前听口，并提示“报嘴后不能换听”；
- 报嘴后将不能用的操作置灰；
- 发财、补牌、杠分和结算显示事件提示。

### 7.3 结算页

- 胡牌牌型；
- 发财数量和发财番；
- 其他番种；
- 自摸/点炮信息；
- 各项杠分；
- 每个玩家本局净得分和累计分数；
- 荒庄时明确显示不结算规则。

## 8. 测试重点

规则引擎至少需要覆盖：

- 120 张牌数量和每种牌数量；
- 起手发财和连续发财补牌；
- 发财不参与胡牌、不允许碰杠；
- 三家通碰；
- 明杠、补杠、暗杠的合法性；
- 别人打出的第四张不能补杠；
- 无发财点炮被拒绝；
- 有发财可以点炮；
- 3 张发财听牌但未报嘴可以自摸、不能点炮；
- 报嘴后听口锁定；
- 报嘴后不能碰杠；
- 报嘴后摸非胡牌必须原张打出；
- 报嘴后摸到胡牌必须胡；
- 报嘴后摸发财并补牌成胡；
- 碰碰胡、清一色、发财番数叠加；
- 自摸、点炮、补杠、明杠、暗杠结算；
- 荒庄时杠分处理；
- 无抢杠胡；
- 一炮多响按本局起牌顺序处理，谁先起牌谁优先；
- 牌墙耗尽和补牌位耗尽。

建议为每个复杂牌局保留事件日志，使失败案例可以重放。

## 9. 开发前需要最终确认的事项

以下事项不影响可行性，但会影响实现细节：

1. 四人具体起手牌数量、庄家是否多一张牌、首轮从谁开始摸牌；
2. 掷骰结果如何映射到起牌位置和摸牌方向；
3. 发财补牌、杠补牌是否共用同一个墙尾；
4. 补牌摸到发财时是否连续补牌；
5. 报嘴后摸到发财且补牌不胡时，是否把补牌原样打出；
6. 各种动作同时发生时的优先级；
7. 清一色是否明确排除红中、白板；
8. 是否只允许标准 4 面子 + 1 将，是否加入七对子等特殊牌型；
9. 是否放弃可胡牌张（定稿已明确：报嘴后自摸不能放弃、点炮可拒；未报嘴自摸可按规则选择）；
10. 暗杠、明杠是否还有额外番数；
11. 牌墙或补牌位耗尽时如何处理；
12. AI 难度、游戏平台和是否需要联网。

---

## 10. 推荐下一步

1. 先确认第9节中的规则边界；
2. 搭建 TypeScript 规则引擎和自动化测试；
3. 用命令行或测试数据跑通一局完整流程；
4. 再制作 React 牌桌 UI；
5. 最后接入 AI 和动画。

不建议一开始就做联网和精美 UI。先让规则引擎能稳定重放和结算，是整个项目成功的关键。
