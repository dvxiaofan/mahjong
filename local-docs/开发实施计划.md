## 一、阅读和维护规则

### 1.1 状态标记

- `[x]` 已完成：实现、测试和验收均已完成
- `[~]` 进行中：当前正在实施；同一时间原则上只保留一个主步骤为进行中
- `[ ]` 待开始：尚未实施
- `[?]` 待确认：需要产品/规则决定后才能冻结
- `[!]` 阻塞：已发现阻塞原因，需外部条件或明确决策

### 1.2 每一步的完成条件

一个步骤只有同时满足以下条件才可以标记为 `[x]`：

1. 代码或文档产物已经落盘；
2. 相关测试或人工验收已经完成；
3. 没有遗留的明显 TODO 影响该步骤目标；
4. 在本台账的“进度日志”中记录结果和 commit；
5. 创建一个本地 Git commit。

### 1.3 Git 约定

- 每完成一个明确步骤就创建一个本地 commit；
- 不自动执行 `git push`；
- commit 前先运行与步骤匹配的检查，并确认 `git diff --check` 通过；
- 不把 `node_modules/`、`dist/` 或本地临时文件提交进仓库；
- 若工作区已有用户修改，先区分归属，不覆盖或混入无关改动。

## 二、项目边界和依据

### 2.1 规则依据优先级

1. [自定义麻将规则.md](../自定义麻将规则.md)：唯一的规则最高依据；
2. [游戏需求文档.md](./游戏需求文档.md)：产品和技术需求；
3. [补充建议.md](./补充建议.md)：审阅意见和收尾记录；
4. 本文档：实施顺序、验收标准和进度记录。

如果分析文档和规则定稿冲突，以规则定稿为准；如果产品需求和当前代码冲突，先记录决策，再修改代码和测试。

### 2.2 当前实现边界

当前仓库是纯 TypeScript 单局规则引擎，核心入口为：

- `createGame()`：创建牌墙并发牌；
- `getLegalActions()`：根据状态生成合法动作；
- `applyAction()`：校验动作并推进状态；
- `getCurrentWaitingTiles()` / `getCurrentFanIfWinning()`：提供 UI 可用的查询。

当前尚未包含：浏览器 UI、正式 AI、多局会话、联网协议、用户账号和部署配置。
