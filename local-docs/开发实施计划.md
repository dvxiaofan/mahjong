## 一、阅读和维护规则

### 1.1 状态标记

- `[x]` 已完成：实现、测试和验收均已完成
- `[~]` 进行中：当前正在实施；同一时间原则上只保留一个主步骤为进行中
- `[ ]` 待开始：尚未实施
- `[?]` 待确认：需要产品/规则决定后才能冻结
- `[!]` 阻塞：已发现阻塞原因，需外部条件或明确决策

### 1.2 每一步的完成条件

一个步骤只有同时满足以下条件才可以标记为 `[x]`：

1. 代码或文档产物已经落盘；
2. 相关测试或人工验收已经完成；
3. 没有遗留的明显 TODO 影响该步骤目标；
4. 在本台账的“进度日志”中记录结果和 commit；
5. 创建一个本地 Git commit。

### 1.3 Git 约定

- 每完成一个明确步骤就创建一个本地 commit；
- 不自动执行 `git push`；
- commit 前先运行与步骤匹配的检查，并确认 `git diff --check` 通过；
- 不把 `node_modules/`、`dist/` 或本地临时文件提交进仓库；
- 若工作区已有用户修改，先区分归属，不覆盖或混入无关改动。

### 1.4 问题记录维护

- 自 2026-09-11 起，按用户要求共同维护 [问题记录.md](./问题记录.md)，可整理表述、更新状态和补充依据，保留原意与稳定编号；
- 问题记录集中展示反馈、处理状态和验收目标；本台账负责实施阶段、顺序和进度日志，状态变更时同步更新；
- 已登记或已明确需求不等于已完成；只有实现和相关验证完成后，才可补充依据并标记为 `[x]`；
- 历史章节中“保留用户问题原文”的表述描述当时的处理方式，后续维护按本节执行。

### 2.2 当前实现边界

当前仓库已包含 TypeScript 规则引擎、React 本地牌桌、三档 AI、多局会话、
WebSocket 联网服务和发布配置。核心规则入口为：

- `createGame()`：创建牌墙并发牌；
- `getLegalActions()`：根据状态生成合法动作；
- `applyAction()`：校验动作并推进状态；
- `getCurrentWaitingTiles()` / `getCurrentFanIfWinning()`：提供 UI 可用的查询。

当前明确不包含用户账号体系和托管式云部署；本地与联网玩法均已可运行。
