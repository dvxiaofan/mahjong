# 同类麻将 UI 调研与改进建议

- **调研日期**：2026-09-12
- **状态**：调研完成；R-01–R-06 已实施并验收，R-07 声音评估暂停，R-08 尚未立项。R-01–R-03 与 C1–C3 见 [界面优化与学习约局验收报告](./界面优化与学习约局验收报告.md)，R-04–R-06 见 [学习约局与教练复盘验收报告](./学习约局与教练复盘验收报告.md)。下文保留调研时的建议与依据。
- **项目基线**：功能代码 `1172d51`；M12 浏览器补验收 `3c39e65`，问题 1–20 已关闭。
- **本轮产物**：来源核实、界面对照、现有实现评估、建议顺序与验收目标。没有修改游戏代码、依赖、牌面或音频资源。

建议继续使用现有 React + CSS，先改善牌桌的信息密度、手机手牌操作和误触保护，再完善教程、复盘与约局入口。已有的中央悬浮出牌、胡碰提示、终局四家亮牌和声音设置应保留。当前没有足够依据支持更换渲染技术或引入更多麻将规则。

## 1. 用户约束与研究方法

本轮按用户要求：先网上调研，再考虑更新；其他方案最多借鉴 UI 设计，规则引擎必须保持独立。

- 规则最高依据仍为 [自定义麻将规则](../自定义麻将规则.md)。120 张牌、发财补牌、禁吃、三家通碰、报嘴、胡牌结构、竞争顺序与计分均沿用本项目约定。
- 合法动作、胡牌与听口、计番、AI 和服务端权威推进继续使用本项目实现。界面只读取座位投影并提交已有合法动作，不再维护另一套规则判断。
- 外部项目用于观察布局、信息层级、交互和反馈；没有安装其包、复制实现或引入其规则配置、算法、协议、声音与图片。以后也由我们独立实现界面，不依赖外部麻将引擎。
- 通过网页搜索寻找候选，再核实官方站点、发行商商店页面和作者仓库。搜索摘要、AI 概览、素材聚合站与用户评论不作为功能或公平性的事实依据。

本轮查看了六个产品/项目。商业产品主要依据官方说明和宣传截图；开源项目另外访问了公开单人演示或教程、查阅界面文件。没有进行商业客户端完整对局、真人组局或手机真机性能测试；外部项目的窄屏适配观察限于官方移动截图与响应式源码，没有完成有效的自定义手机视口实测。静态截图可以说明布局，不能证明动画时长、点击规则或实际语音行为。

## 3. 哪些设计适合我们

| 维度 | 观察依据 | 本项目可借鉴的方向 | 适配时的取舍 |
|---|---|---|---|
| 牌桌结构 | S1、S2、S4、S5 将手牌、牌河和局况围绕同一桌面组织 | 缩短看牌、看来源、选动作之间的视线距离；给核心牌区更多空间 | 保留四向身份；各家弃牌仍归入各自区域，中央继续承担暂时的大牌与动作提示 |
| 信息密度 | S4 演示没有为每家重复铺开大段状态说明；S5 把日志放侧边 | 收紧重复边框、空区域、标签和装饰间距；完整记录按需打开 | 发财、碰杠、报嘴、来源与分数不能因“简洁”被隐藏或混淆 |
| 牌面可读性 | S4 的摸牌与原手牌有间隔；S6 截图中透视和背景纹理很强 | 保留新摸牌间隔与高亮，降低牌背后纹理的存在感 | 牌面继续使用已核对的本地 PNG；桌面方向感可以通过座位位置表达，读牌不必依赖旋转文字 |
| 关键反馈 | S2 牌桌图有带角色来源的动作提示；S3 图中有明显中文大字结果 | 明确“谁做了什么”；重大事件与普通出牌分层 | 当前中央悬浮实现已满足用户要求，不重复开发；延迟与动画以本项目真实状态为准 |
| 操作保护 | S1 手册专门解释双击摸切与误操作，并记录和牌选项出现时的限制 | 手机增加可选的选牌确认，滚动手牌不能意外出牌 | 这是我们的改进建议，不声称六款产品都使用同一交互方式 |
| 入门说明 | S2 有教程；S5 实际教程把目标牌高亮并贴近显示一句引导 | 将我们的特殊规则拆成短场景，从真实牌局动作学习 | 教程必须由本项目规则生成；不导入日麻役种、振听、立直或其他地方玩法 |
| 复盘 | S1 手册、S4 牌谱入口、S5 回放 UI、S6 记录能力 | 在已有逐步回放上增加关键节点，方便回到“为什么不能胡”的局面 | 我们已有回放，不将它当作待新增功能；局中回看仍按原座位权限显示 |
| 熟人约局 | S2 房间截图把四个座位与 Ready 状态并排展示；S3 官方强调好友约战 | 明确房主、空位、在线和托管状态，减少入桌过程中的疑惑 | 本项目已有字段可先改善呈现；真正的“准备/开始”门槛属于房间流程变更，不能只画一个 Ready |
| 声音 | S2 官方的角色 CV 与表情；S4 的声音控制及音频 UI 文件 | 先优化现有报牌的节奏、可懂度和音量，再考虑可选提示音 | 公开事件播报、角色语音、实时语聊是不同功能，不能相互充作需求证据 |

## 4. 对当前项目的判断

### 已经具备，应继续保留

- [MahjongTable](../web/components/MahjongTable.tsx)、[TableCenterLayer](../web/components/TableCenterLayer.tsx) 和 [TableDiscardOverlay](../web/components/TableDiscardOverlay.tsx) 已将新弃牌和动作提示放在独立浮层；等待响应时保留大牌，结束后归入来源区域。当前至少展示 800ms、飞行 320ms，不增加玩家模块高度。
- [PlayerSeat](../web/components/PlayerSeat.tsx) 与 [ResultPanel](../web/components/ResultPanel.tsx) 已在任意玩家胡牌后亮出四家最终手牌，并单独标记胡牌张、解释实际分组。不能套用某些日麻产品只展示特定玩家手牌的习惯。
- [TableAudio](../web/components/TableAudio.tsx) 已有公开报牌、主静音、独立语音/音效及音量；[WinHelp](../web/components/WinHelp.tsx) 已能解释自己的胡牌资格。没有必要为了与竞品对齐重做这些能力。
- [HistoryDrawer](../web/components/HistoryDrawer.tsx) 已支持步骤滑杆、前后步进、返回实时、事件分类和点击动作回放。后续应改善寻找关键局面的效率。
- 规则引擎、座位投影和 UI 已分层；本地与联网合法动作仍由自有引擎决定。这一边界足以支撑 UI 优化。

### 仍有改进空间

当前布局已经解决重叠与页面横向溢出，但窄屏仍然需要较长的纵向浏览，自己的手牌也依赖局部横向滚动。[styles.css](../web/styles.css) 在 820px 以下把玩家区分行，在 520px 以下将我方牌缩为 31×47px。M12 补验收说明帮助区可以正常换行，没有证明整个操作场景已足够紧凑。

多处同时展示来源、轮次和操作说明有助于纠错，但会增加常驻文字与视线移动。应统一主提示，细节随用户展开；保留文字、图标与焦点状态，避免只用颜色表达“轮到你”。

还有两个不能混入纯 UI 工作的依赖：

1. 联网倒计时：自有 [lobby.ts](../src/lobby.ts) 在服务端维护 `actionDeadlineAt`，但 `LobbyRoomView` 和 [RoomSnapshot](../src/room.ts) 当前不含截止时间。准确倒计时需要自有协议单独设计，不能收到页面状态就擅自从 12/30 秒重计。
2. 房间准备：公开成员有 `connected`、`trustee`、`isHost`，没有竞品式 Ready 状态。可以先改善已有状态的展示；新增准备阶段需另做房间生命周期设计。

## 5. 候选更新与验收目标

以下为调研时的**建议与验收目标**；实施状态以文首所链接的验收报告为准。优先级依据本项目已出现的反馈和当前界面，不是竞品的功能数量。

| 编号 | 顺序 | 候选项 | 预期收益 | 主要范围 |
|---|---|---|---|---|
| R-01 | 优先 | 牌桌布局与信息减负 | 当前牌、来源、手牌和动作更容易同时看清 | 自有 React 组件与 CSS |
| R-02 | 优先 | 手机手牌与选牌确认 | 减少横向找牌和滑动误出牌 | 我方手牌、操作区、本地偏好 |
| R-03 | 优先 | 整合已有轮次、响应与提交提示 | 减少重复文字，突出当前主提示 | 既有视图与请求状态的展示 |
| R-04 | 后续 | 自定义规则的短教程 | 在具体牌面上学会发财、报嘴和成牌 | 自有引擎构造的独立教学场景 |
| R-05 | 后续 | 关键节点复盘 | 快速定位报嘴、碰杠、胡牌前后的局面 | 既有动作记录与回放界面 |
| R-06 | 后续 | 房间状态与邀请入口 | 熟人更容易找到房间、确认自己已入座 | 既有公开房间字段；不包含新准备机制 |
| R-07 | 评估后再做 | 声音细节 | 提高连续动作时的可懂度 | 现有本地声音与偏好 |
| R-08 | 需单独设计 | 服务端计时的可见反馈 | 说明真实剩余时间和超时结果 | 自有协议与房间计时，之后再接 UI |

### R-01：先做紧凑牌桌原型

顶部保留简短局况；其他三家的身份、分数、发财、碰杠和弃牌围绕桌面排列，减少空区占高。我方手牌与操作保持相邻。中央大牌继续悬浮；完整牌局动态、规则细节与历史可放入已有抽屉或可展开区。

先比较“收紧现有布局”和“窄屏固定我方操作区”两个原型。固定操作区必须预留空间并兼容安全区、浏览器工具栏和放大字体；不能遮住最后一排牌河。

验收目标：1280×720、844×390、390×844、320×700 都能看清最新弃牌与来源、抵达所有合法动作；横屏普通局面完整手牌与操作同时可见。多弃牌、四副碰杠、长名字、四张发财、观战和终局均不重叠。大牌出现、等待和归位不改变玩家模块高度。终局四家仍完整亮牌。

### R-02：为手机独立设计手牌操作

横屏争取保留完整一行；竖屏比较分行手牌与局部滚动两种方案。若分行，可在 390px 试两行、320px 试三行，让触控区域有空间，而不是不断缩小整桌。建议以主要操作约 44×44 CSS px 为设计目标；14 张牌在 390px 内无法同时满足单行与每张 44px 宽，这是需要取舍的几何限制。

提供可选的“先选牌，再打出”：第一步清楚显示牌名和选中牌，第二步在我方区域确认；桌面原有快捷操作可保留。候选牌只属于界面状态，最终仍提交当时引擎提供的合法动作。页面滚动、快照变化、新局、断线和提交期间应取消或重新核对选择。

验收目标：手指拖动不会出牌；相邻同牌选择可辨认；确认前后牌名、图案和提交牌值一致；有胡/碰/杠选择、报嘴锁定、重复点击与断线恢复时均不会误提交。键盘能选到并确认，焦点可见。牌面映射与原有动作回归继续通过。

### R-03：让主提示有唯一的当前含义

现有代码已经区分“轮到你选择”“你已响应，等待其他玩家”“操作提交中，等待确认”；本项整合它们的展示位置与信息层级。来源、大牌和按钮共享当前局面，次要说明可按需展开。响应按钮位置尽量稳定，新的提示不能把指针下的“过”挤成另一个动作。

验收目标：连续三家出牌、先报嘴再胡、他人碰杠、请求拒绝与重试、回放跳转和重连时，不遗留旧来源、旧可用按钮或旧播报。浮层继续允许点击穿透，声音和动画完成与否不参与规则推进。R-01–R-03 可以分步提交，沿用 M8/M9 已建立的边界用例。

### R-04–R-07：在现有能力上继续完善

- **短教程**：首先设计四个自有例子——三/八/九条未成组、零财自摸与接炮的差别、三财先报嘴再胡、杠后补牌。只借 S5 的目标高亮与一句话引导。每一步由真实合法动作推进，随时退出，不改普通对局与存档。
- **关键节点复盘**：在现有滑杆和动作列表上增加报嘴、碰杠、胡牌前后的定位入口；同一条动作可能产生多个事件，不能把事件序号直接当作回放步数。验收要核对跳转前后真实牌面，并保持当前座位的历史可见范围；回放不补播现场语音。
- **约局入口**：先展示真实的房主、空位、连接和托管状态，可提供复制房间信息的入口。邀请内容不包含恢复令牌或自动公开房间密码；用户自主分享。真正的准备按钮不纳入此 UI 项。
- **声音细节**：先实测现有普通话在连续出牌、碰后出牌、胡牌时的顺序和音量，再判断是否需要“轮到你”的短提示。保留主静音、独立音量、后台静音和历史快照不补播。角色音色或表情包可以后评估，不作为本阶段的前置条件。

### R-08 与暂缓方向

R-08 应先设计自有协议怎样表达服务端截止时间、对应的阶段/修订号，以及重连后的剩余时间。显示为零时也应等待服务端结果，前端不能自行判定过牌或托管；本地模式不凭空增加联网超时限制。

实时语聊暂缓。它需要独立的音频通道、麦克风开关、回声处理与断线恢复，现有报牌音频不能代替这些工作；是否加入应根据熟人约局的实际使用需要决定。新番种、多地方玩法、匹配排行榜、角色养成和 3D 主题也不进入本轮候选实施；如果以后扩展玩法，仍由我们独立修改规则文本、引擎与测试。

## 6. 界面实现方案取舍

这是对本项目的技术判断，不能从宣传截图反推商业产品采用了 Unity、Cocos 或某种服务端框架。

| 方案 | 对本项目的价值与成本 | 建议 |
|---|---|---|
| 继续 React + DOM/CSS | 复用牌面、按钮、焦点、投影和现有回归；可分别约束牌区、信息区及浮层；S4/S5 也表明网页牌桌可以用 DOM/CSS 组织 | 当前首选，先做 R-01–R-03 |
| 整桌统一缩放 | 容易保留空间关系，但缩小后文字、牌和触控目标一起变小；不能单独解决手机操作 | 可用于只读缩略预览，交互区域单独布局 |
| Canvas/Pixi 一类绘制层 | 可能适合大量视觉效果，但要另做点击命中、焦点和可访问语义，并迁移既有 UI 验收 | 先有本项目性能数据再评估，本轮不引入 |
| WebGL 或原生 3D 客户端 | 能提供透视与空间效果，也增加相机、资源、输入及设备适配工作；S6 仅证明原生路线存在 | 当前投入与主要问题不匹配，暂缓 |

没有测得本项目必须更换渲染技术的性能瓶颈。选型目标先放在牌面清楚、动作准确、状态可信；组件规模或效果数量上升后，再用本项目设备实测评估。
