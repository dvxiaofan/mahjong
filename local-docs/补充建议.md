## 一、引擎与规则文档的现存冲突（需改代码）

**争抢优先级不一致**：

- 规则文档第三章/第五章：「打出这张牌的**下家**优先，沿逆时针依次判定」
- 引擎实现：`claimOrder`（`src/game.ts:62`）从**庄家起牌顺序**计算优先级
- 后果：当弃牌者不是庄家时（如 2 号打牌、3 号碰、0 号胡），引擎会让 0 号胡、规则应判 3 号碰
- 修复：`claimOrder` 改为 `seatOrderFrom(nextSeat(discarder))`，并同步修正 game.test.ts:178 的测试语义（该测试弃牌者恰为庄家，两种规则碰巧同序，区分不出）

## 二、测试缺口（M1 收尾清单）

现有 21 个测试覆盖了流程与判定，但**结算金额类断言为零**：

1. 自摸胡：三家各付 `1 + 番数`（含番种明细验证）
2. 点炮胡：仅点炮者付 `1 + 番数`
3. 暗杠：终局三家各付 1；明杠：终局点杠者付 1（有人胡时结算、荒庄时不结）
4. 补杠：即时付 1；荒庄时退还（荒庄退还已有测试，正常结算路径没有）
5. 0 财不能点炮胡（`fortuneCount < 1` 分支）
6. 一炮多响：两人同时声明胡，按弃牌者下家顺序只认第一家
7. 规则文档「结算示例」6 个场景全量断言（含「3 财已报嘴清一色+碰碰胡点炮=6」）

## 三、规则文档尚未覆盖的新边界（需用户确认）

1. **拒炮后第二家能否胡？** 报嘴玩家拒了第一家的炮，按座位顺序第二家声明胡算不算数。引擎现状：等齐三家响应后取顺序内第一个非 pass 声明，即拒炮后下家可胡。规则文档「一炮多响只认第一家」未写拒炮场景，建议按引擎行为明确写入
2. 报嘴玩家在 claiming 阶段「先报嘴再胡点炮」已被引擎支持且有测试（game.test.ts:114），规则文档第六章第 1 条语义兼容，建议补一句明确「报嘴可与胡牌声明在同一响应窗口内完成」

## 四、联机版设计缺口（M4 前置，当前文档只有路线图）

《游戏需求文档》2.3 节列了功能清单但没有设计说明。真正要做的新东西按优先级：

| # | 事项 | 说明 | 优先级 |
|---|---|---|---|
| 1 | **状态投影** `projectStateForSeat(state, seat)` | 当前 `GameState` 全透明，联机上直接广播 = 对家手牌泄露。只暴露自己暗牌 + 公共信息。**必须在 UI 之前设计**，因为 UI 渲染依赖投影后的视图 | 最高 |
| 2 | **多局会话层** | 引擎只管单局。需 Match/Session 模块：上局赢家做庄、跨局累计分、一场 N 局、平局处理 | 高 |
| 3 | **服务端与部署选型** | 引擎纯函数可直接跑服务端。建议评估 Cloudflare Durable Objects（WebSocket + 有状态房间，一个 DO 实例 = 一张牌桌，纯 JS 引擎可直接入 Workers） | 高 |
| 4 | **断线重连** | 引擎快照 + 事件日志已支持回放，只差协议层封装 | 中 |
| 5 | **超时托管** | claim 窗口超时默认注入 pass（`allResponsesReceived` 同步模型已为此铺路）；出牌超时的策略待定 | 中 |

并发问题已被「等齐三家响应才决胜」的同步模型消掉，不需要复杂并发设计——这一点比《游戏需求文档》60 行的预判乐观。
