## 0. 一句话结论

“麻将概率助手电脑版”不是一个麻将规则引擎，而是一个**第三方牌桌读屏 + 概率建议器**。它最值钱的部分是“手牌向听/进张 → 逐家危险度 → 备选出牌 → 本地复盘”的分析链，而不是它用来读别人牌桌的计算机视觉。

本项目已经有更可靠的权威牌局状态、规则引擎、AI 和回放记录。正确做法不是把 Python 读屏程序搬进来，而是把这套分析链**用 TypeScript 重写成“教练 / 复盘”能力**，直接消费我们自己的 `GameView` 和 `records`。

## 2. 助手项目拆解

### 2.1 运行形态与依赖

交付目录只有 Windows 打包产物，没有随附源码：

- `MahjongDesktopAssistant.exe`：PE32+ x86-64 GUI 程序，约 5.8 MB；
- `_internal/`：约 216 MB，包含 Python 3.13 运行时、Tkinter、OpenCV、NumPy、Pillow、ONNX Runtime、psutil 等；
- `_internal/models/pretrained/weights.onnx`：约 12 MB，42 类牌面检测模型；
- `DESKTOP_README.md`：说明它是“读取已打开的微信小程序牌局，只给建议，不操作游戏”。

解包后可确认的主模块：

| 模块                      | 作用                                                                 |
| ------------------------- | -------------------------------------------------------------------- |
| `mahjong_probability.pyc` | 纯分析内核：向听、听牌、进张、逐家风险、Monte Carlo、快照分析        |
| `desktop_assistant.pyc`   | Windows 窗口读取、Tkinter 主窗与悬浮卡、识别编排、手动副露、复盘记录 |
| `yolo_screen_detect.pyc`  | 42 类 ONNX 牌面检测、坐标还原、NMS                                   |
| `wall_counter.pyc`        | 牌墙余数的小区域 OCR（七段式数字模板）                               |
| `training_journal.pyc`    | 本地 JSONL 决策日志                                                  |

它的工作流是：

1. 枚举可见 Windows 窗口，选择微信/游戏窗口；
2. 截取窗口客户区，约每秒 1 帧；
3. YOLO 检测全桌牌面；
4. 从靠下边缘的检测框中挑“自己的手牌行”；
5. 用固定比例区域估计三家牌河；
6. 识别自摸按钮、牌墙余数；
7. 调用概率内核，渲染置顶悬浮建议卡；
8. 把稳定建议与随后识别到的实际弃牌配对，写入本地复盘。

### 2.2 识别管线：能看出设计巧思，也能看出脆弱点

**手牌行选择**比“直接取最下面一排”稳健一些：

- 分别检查上、下、左、右四条边缘带（各占画面 20%）；
- 对每条边缘带，以每个检测框为锚点，按对应方向的容差（画面宽/高的 5.5%）聚类；
- 以 `(数量, 置信度和)` 最大的一组作为该边缘的候选行；
- 再按对应方向的间距拆分连续段，间距阈值约为中位牌宽的 1.8 倍；
- 取最大连续段，并在四条边缘的候选行中选出 `(数量, 置信度和)` 最大的一组，避免把上方副露/花牌一起算进手牌。

这个“先聚类、再拆连续段、取最大段”的思路，对任何“一排牌中间有缺口”的场景都有效。本项目不需要读屏，但如果未来做第三方牌桌导入，这部分值得参考。

**三家牌河**则完全是固定比例启发式：

- 上方：画面高度 18%–45%，取最大横排；
- 下方：44%–73%，取最大横排，并排除自己手牌；
- 左侧：横坐标 15%–39%，取最大纵列；
- 右侧：61%–86%，取最大纵列；
- 检测到至少 3 张时才把这些框标记为“已占用”，避免与下方自家牌河重复；少于 3 张仍会返回候选，但可靠性更低。

这意味着它对窗口比例、缩放、皮肤、遮挡和动画非常敏感。README 也明确说“公牌、牌河和副露识别仍属试验阶段”。

**自摸按钮**用 HSV 橙色掩码 + 连通域，限制在画面中下部 58%–82% 宽、52%–84% 高，再按最小边长、长宽比、填充率、面积过滤。**牌墙余数**用固定的中上部绿色数字区域，配合七段式模板匹配，识别不到就返回 `(None, 0)`，不会沿用旧数字。这个“低置信度就不显示”的原则值得保留。

**识别层的结论**：

- 设计上有可借鉴的鲁棒性技巧；
- 但整体依赖特定游戏 UI，跨游戏/跨分辨率不可直接用；
- 本项目是自有牌桌，状态来自引擎，**没有任何理由引入 12 MB 模型和 OpenCV 依赖**。

### 2.3 分析内核：真正值得研究的部分

#### 牌模型

助手使用 34 种普通牌（各 4 张）+ 8 张花牌（各 1 张），共 144 张：

- `0–8` 万、`9–17` 筒、`18–26` 条；
- `27–33` 东南西北中发白；
- `34–41` 春夏秋冬梅兰竹菊；
- `DECK_COUNTS = 34 × 4 + 8`。

它支持标准型、七对子、十三幺的胡牌判断。**这三条不能直接搬到本项目**：我们的规则只有标准型 4 面子 + 1 将，没有七对子/十三幺，也没有风牌和花牌。

#### 向听

核心是一个带缓存的 DFS：

- 递归枚举刻子、顺子、对子、搭子；
- 用 `8 - 2 × 面子 - 搭子 - 将` 计算向听；
- 对子/搭子数量按剩余面子数封顶；
- 支持已副露的组数；
- `-1` 表示已胡，`0` 表示听牌。

这套思路与本项目 `src/ai-evaluation.ts` 的 `calculateShanten()` 基本同源。我们的实现已经针对自定规则做了裁剪，且带有缓存和测试，**不需要替换**。

#### 听牌与进张

- `waits(hand, openMelds)`：枚举 34 种牌，若加入后成胡，则记录“理论剩余张数”；
- `improving_tiles(hand, visible, openMelds)`：枚举 34 种牌，若加入后向听下降，则记录“物理剩余张数 = 4 − 自己手牌 − 已见牌”。

注意：`waits()` 本身只看手牌，不扣已见牌；`discard_analysis()` 输出时再用 `remaining` 字典扣减。这个分层本身没问题，但移植时不能把 `waits()` 的原始数字直接当成“牌山还剩几张”。

#### 弃牌分析

对每个不同弃牌 `d`：

1. 从手牌移除一张 `d`；
2. 计算剩余手牌的听牌 `waits`；
3. 计算有效进张 `improving_tiles`；
4. 对三家分别计算危险度；
5. 汇总为 `ukeire`、`risk_summary`、`opponent_risk`；
6. 按 `(-ukeire, 风险等级和, 牌id)` 排序。

这里有一个**实现层面的细节**：内核排序没有显式把 `shanten` 放在第一键，主要按进张数排序。桌面 UI 在拿到结果后会重新按 `(shanten, 是否接近最佳进张, 风险, 牌效, ...)` 排序。所以如果直接复用内核排序，可能把“向听更好但进张略少”的牌排到后面；迁移时应使用我们自己的排序键。

#### 逐家危险度

`_risk_for_opponent()` 是一个可解释的启发式评分，不预测对手暗手：

| 条件                       |                        分数变化 |
| -------------------------- | ------------------------------: |
| 该家牌河里已打过这张牌     |                            −5.0 |
| 同花色存在“筋”牌（相差 3） |                            −0.7 |
| 幺九牌                     |                           −0.25 |
| 3/7 牌且巡目 ≥ 7           |                            +0.6 |
| 该家有副露                 |                            +1.4 |
| 巡目推进                   | `+0.12 × min(max(turn, 0), 12)` |

分数映射：

- `≤ −1.5`：低
- `< 0`：偏低
- `< 1.2`：中
- `< 2.4`：偏高
- 其余：高

每条判断都会附带一条中文证据，例如“该家已打过此牌：对该家有强安全证据”。这一点很适合我们的“可解释 AI”原则。

但必须指出：

- `visible` 形参传入了函数，**实际没有参与评分**；
- “有副露”只判断有无，不区分碰/杠的牌种和花色；
- 没有考虑对手报嘴/听牌状态、剩余牌数、番种价值；
- 筋牌逻辑只按“相差 3”判断，未区分“对手打过 4”与“对手打过 1/7”的强度差异，也没有结合牌河位置；
- 这些分数和区间都**未经牌谱校准**。

#### 点炮粗估区间

等级映射为：

| 等级 | 粗估区间 |
| ---- | -------: |
| 低   |    1%–3% |
| 偏低 |    2%–6% |
| 中   |   4%–10% |
| 偏高 |   9%–18% |
| 高   |  16%–30% |

三家合并时按独立事件处理：`1 − Π(1 − p_i)`。这只能叫“粗估”，不能叫真实概率。助手 README 也明确写了“未经实战牌谱校准”。

#### Monte Carlo 和牌率

`draw_probability()` 的设计：

- 从手牌 + 已见牌重建未知牌池；
- 34 种牌按 `4 − 自己 − 已见` 放入牌池，花牌按 `8 − 已见花牌` 放入；
- 默认 `trials=20000`、`seed=7`、`opponent_draws_per_turn=3`；
- 每轮先让对手消耗未知牌，再摸自己的牌；
- 摸到花牌则连续补摸，直到非花；
- 每次摸牌后判断胡/听；
- 若手牌到 14 张，枚举所有弃牌，选择“向听最小”的一张继续；
- 输出 `tenpai_rate`、`self_draw_win_rate`。

它的边界很清楚：

- 不模拟对手的碰/杠/弃牌；
- 不模拟点炮胡；
- 弃牌策略只按向听最小，不按进张/番种；
- 假设 14 张手牌的最后一张就是刚摸的牌（`concealed[:-1]`）。

这套模拟适合做“未来 N 巡内听牌/自摸”的粗略参考，不适合直接当作胜率。

### 2.4 悬浮卡与复盘日志

悬浮卡的信息层级很值得借鉴：

1. 顶部：牌墙余数 + 图像匹配度；
2. 手牌行：实际牌面、副露、剩余张数；
3. 首选建议：大号牌面 + 向听 + 理论进张 + 点炮粗估；
4. 备选 2/3：较小牌面 + 向听/进张/风险；
5. 底部：规则口诀、识别置信度、未登记副露的警告。

它还处理了几个真实交互问题：

- 检测到“自摸”按钮时暂停弃牌建议；
- 手牌出现四张相同牌时提示“可能正在杠”，不把这四张当弃牌；
- 支持手动登记碰/吃/杠，按实际副露修正手牌张数；
- 牌墙读数低置信度时隐藏，不沿用旧数字；
- 建议卡可拖动/收起，且不操作游戏。

复盘日志 `training_journal.pyc` 的设计：

- 文件：`%LOCALAPPDATA%\MahjongProbabilityAssistant\replay.jsonl`；
- 每局 `begin_round()` 生成 12 位 ID；
- `observe(payload)` 在“14 张、有推荐”时记录待定快照；
- 下一次变成 13 张且只少一张牌时，配对为一次 `decision`；
- 记录 `hand_before`、`recommendations`、`actual_discard`、公开牌数、牌河数；
- 局末记录 `round_result` 与 `net_score`；
- 不上传截图，不联网，不自动训练。

这是本项目最应该借鉴的数据设计之一：**不记录“AI 说了什么”就完事，而是记录“当时建议什么、实际打了什么、结果如何”**。

## 3. 本项目现状

### 3.1 已经具备的能力

本项目的核心优势是“权威状态 + 可解释 AI + 完整回放”：

- `src/rules.ts`：胡牌、听牌、番种、报嘴、胡牌分组；
- `src/game.ts`：回合状态机、合法动作、结算；
- `src/ai-evaluation.ts`：标准向听、有效进张、公开可见剩余张数、清一色/碰碰胡潜力、发财番数；
- `src/ai-strategy.ts`：出牌评分、碰/明杠/暗杠/补杠/报嘴评估；
- `src/ai-difficulty.ts`：休闲/标准/进阶三档；
- `src/ai-simulation.ts`：批量整局模拟与最优弃牌率；
- `src/view.ts`：按座位裁剪隐私投影，联网只暴露合法信息；
- `web/localSession.ts`：seed + 动作 records，可重建任意回放步骤；
- `web/components/HistoryDrawer.tsx`：现有回放抽屉；
- 完整质量门禁：规则、联网、UI、声音、牌面、验收测试。

### 3.2 当前缺口

| 缺口          | 现状                                            | 影响                            |
| ------------- | ----------------------------------------------- | ------------------------------- |
| 对手危险度    | AI 评估只看自己手牌与公开剩余张数，没有逐家风险 | 后巡可能打出危险中张            |
| 和牌/听牌概率 | 没有 Monte Carlo 或解析概率                     | 玩家看不到“再摸几巡”的量级      |
| 教练面板      | 没有面向玩家的“为什么打这张”                    | 现有 AI 原因只在开发/回放数据里 |
| 决策质量复盘  | 回放能看动作，但不能回答“这步打得好不好”        | 学习价值未释放                  |
| 风险指标      | AI 模拟只统计胡/荒庄/最优弃牌率                 | 无法评估“防守是否变好”          |

### 3.3 抽样验证：现有 AI 的防守盲区

为了确认“风险层”是否真的有价值，我用现有进阶 AI 跑了 40 局（种子 9000–9039），共 2057 次弃牌决策：

| 指标                                              |           结果 |
| ------------------------------------------------- | -------------: |
| 按现有策略评分选到第一                            |           100% |
| 同时选到“最高进张”                                |         37.58% |
| 弃牌已在至少一家牌河（现物）                      |         44.24% |
| 决策时至少一家有副露                              |         77.59% |
| 后巡（≥8 张弃牌）决策                             |         848 次 |
| 后巡打出“无人打过的中张”                          |         22.41% |
| 存在“同向听、进张差 ≤2、且对手已打过”的更安全替代 | 89 次（4.33%） |
| 现有 AI 采用该安全替代                            |           0 次 |
| 采用安全替代的平均进张损失                        |        0.73 张 |

这不是胜率实验，只说明一个事实：**现有 AI 的评分是“牌效 + 番种潜力”导向，完全没有把“对手已经打过这张”纳入决策。** 在 4.33% 的决策里，存在几乎不损失进张的安全替代；在后巡，22.41% 的弃牌是无人打过的中张。风险层有明确的改进空间，但不应夸大——它不是每手都能救命的万能模型。

具体样本：

- 种子 9000，第 4 巡：现有 AI 打 `p4`（进张 64），安全替代 `p5`（进张 63），当时 1 家副露；
- 种子 9003，第 6 巡：现有 AI 打 `p8`（进张 60），安全替代 `p7`（进张 58），当时 2 家副露；
- 种子 9000，第 6 巡：现有 AI 打 `m7`（进张 58），安全替代 `p8`（进张 58），当时 3 家副露。

这些例子与助手“进张差不超过 2 时，让风险影响排序”的思路一致。

## 4. 逐项可复用性矩阵

| 能力               | 助手实现            | 本项目现状           | 判断             |
| ------------------ | ------------------- | -------------------- | ---------------- |

| 逐家危险度         | 启发式评分 + 证据   | 无                   | **重写采纳**     |
| 点炮粗估区间       | 等级映射 + 独立合并 | 无                   | **改造采纳**     |
| Monte Carlo 和牌率 | 未知牌池 + 对手消耗 | 无                   | **改造采纳**     |
| 手牌行聚类         | 四边缘带 + 连续段   | 不需要读屏           | **仅作未来参考** |
| YOLO 牌面检测      | 42 类 ONNX          | 不需要               | **不采纳**       |
| 牌墙 OCR           | 固定 ROI + 七段模板 | 引擎直接知道牌墙     | **不采纳**       |
| 自摸按钮检测       | HSV + 连通域        | 引擎直接知道阶段     | **不采纳**       |
| Tkinter 悬浮卡     | 置顶、可拖动        | React 牌桌已有信息栏 | **只借鉴层级**   |
| 本地复盘日志       | JSONL 决策配对      | 已有 seed + records  | **改造采纳**     |
| 低置信度隐藏       | 识别不到就不显示    | 可用于“信息不足”提示 | **借鉴原则**     |
| 手动副露登记       | 碰/吃/杠            | 引擎自动维护         | **不采纳**       |

## 5. 建议采纳的四个方向

### 方向 A：把“风险层”加到现有评估（最高优先级）

不要改规则引擎，也不要在 `src/rules.ts` 里塞风险逻辑。新增独立模块，例如 `src/advice.ts`，输入 `GameView`（而不是 `GameState`），输出每张候选弃牌的：

```ts
interface OpponentRisk {
  seat: Seat;
  level: '低' | '偏低' | '中' | '偏高' | '高';
  score: number;
  evidence: string[];
}

interface AdviceOption {
  tile: NormalTile;
  shanten: number;
  waits: { tile: NormalTile; remaining: number }[];
  effectiveTiles: { tile: NormalTile; remaining: number }[];
  ukeire: number;
  riskByOpponent: OpponentRisk[];
  riskSummary: '低' | '中' | '高';
  pointOffRange: [number, number];
  reasons: string[];
}
```

建议的风险因子（按本项目规则调整）：

| 因子                     |                建议权重 | 说明                                     |
| ------------------------ | ----------------------: | ---------------------------------------- |
| 对手牌河已有该牌（现物） |                    −5.0 | 对那一家是强安全证据                     |
| 同花色筋牌               |                    −0.7 | 我们仍有顺子，但比日麻弱，建议保留小权重 |
| 幺九牌                   |                   −0.25 | 连接度低                                 |
| 3/7 牌且后巡             |                    +0.6 | 中张后巡更危险                           |
| 对手有副露               |                    +1.4 | 手牌更集中                               |
| 对手已报嘴               |                    +1.2 | 公开的听牌信号，比“有副露”更强           |
| 巡目推进                 | `+0.12 × min(turn, 12)` | 与助手一致，后续可校准                   |
| 该牌已见 3 张            |                    −0.2 | 剩余张数少，威胁下降                     |

注意：

- 我们只有红中/白板两种字牌，没有风牌；不能照搬“孤张风牌优先”的口诀。
- 我们禁吃，副露只有碰/杠，副露的“形状集中”信号比含吃的规则更强。
- 报嘴是公开状态，可以作为强威胁信号；`lockedWaits` 是私有字段，绝不能读。
- 风险等级先沿用助手的阈值，但界面必须标注“粗估/启发式”，不能写成真实概率。

### 方向 B：做“教练面板”，而不是第二个 AI

现有牌桌已经有右侧信息栏。教练面板应放在**右栏或抽屉**，不要放到手牌下方，避免再次出现“手牌位置忽高忽低”的问题。

建议内容：

```text
教练 · 第 6 巡
现在打  [p5]
距离听牌  1 向听
理论进张  36 张
对家危险度  低 · 中 · 偏高

为什么
- 打 p5 后仍保持 1 向听
- 下家牌河已有 p5，对下家是现物
- 保留 m3/m4 的顺子搭子

备选
[p8] 1 向听 · 34 张 · 危险度 高
[s2] 1 向听 · 32 张 · 危险度 中
```

展示原则：

- 默认关闭，只在本地对局/回放中开启；
- 联网对局默认不显示，避免影响公平性；如要开放，必须只基于 `GameView` 的公开信息，并在产品上明确说明；
- 首选只给一张，备选最多两张；
- 每条建议必须有“为什么”，不能只给分数；
- 风险用“低/中/高”或区间，不用“胜率 62%”这种伪精确数字；
- 面板不改变手牌坞高度，不遮挡牌河和操作按钮。

### 方向 C：把复盘从“动作时间线”升级为“决策质量报告”

现有 `web/localSession.ts` 已经能用 seed + records 重建任意步骤，这比助手的截图日志更可靠。建议新增 `web/review.ts`：

```ts
interface DecisionReview {
  step: number;
  turn: number;
  actualDiscard: NormalTile;
  recommendedDiscard: NormalTile;
  actualShanten: number;
  bestShanten: number;
  actualUkeire: number;
  bestUkeire: number;
  riskLevel: '低' | '偏低' | '中' | '偏高' | '高';
  matched: boolean;
  note: string;
}
```

在回放抽屉中增加“复盘”页签，展示：

- 推荐一致率；
- 平均向听损失；
- 平均进张损失；
- 高风险弃牌次数；
- “有安全替代但没打”的次数；
- 报嘴时机、关键碰杠、首次听牌、胡牌/荒庄节点。

实现上不需要把分析结果写进存档：回放时按需重算即可。这样不会污染现有 `records`，也不会引入版本迁移。

### 方向 D：让 AI 也使用风险层（但分难度）

现有 `rankStrategicDiscards()` 的评分是“牌效 + 番种潜力”。建议新增可选参数或新函数：

```ts
rankStrategicDiscards(state, seat, {
  riskWeight: difficulty === 'advanced' ? 1 : difficulty === 'standard' ? 0.5 : 0,
});
```

约束：

- 只在“同向听、进张差 ≤2”的候选之间用风险重排；
- 不用风险覆盖明显的进张优势；
- 风险权重按难度递增；
- 保持确定性（风险来自公开状态，不需要随机）；
- 在 `AiSimulationSummary` 增加 `dealInCount`、`riskyDiscardCount`、`safeAlternativeTaken` 等指标，做 A/B 对比。

## 6. 适配设计：把助手算法映射到我们的规则

### 6.1 牌模型映射

| 助手牌 id | 含义             | 本项目对应                                               |
| --------- | ---------------- | -------------------------------------------------------- |
| `0–8`     | 万               | `m1–m9`                                                  |
| `9–17`    | 筒               | `p1–p9`                                                  |
| `18–26`   | 条               | `s1–s9`                                                  |
| `27–33`   | 东南西北中发白   | 仅 `red`（红中）/`white`（白板）有对应；无风牌、无“发”牌 |
| `34–41`   | 春夏秋冬梅兰竹菊 | 无对应                                                   |
| 花牌补摸  | 摸到花牌后补一张 | 我们的“发财”是宝牌：摸到即亮出、从墙尾补牌、不计入手牌   |

本项目是 120 张牌：万/筒/条各 36 张 + 红中 4 + 白板 4 + 发财 4。**不能把助手的 144 张牌池、花牌补摸和七对子/十三幺逻辑直接搬过来。**

### 6.2 向听/进张：保留我们自己的实现

我们已经有 `calculateShanten()`、`evaluateHand()`、`getWaitingTiles()`，并且已经处理：

- 副露后的手牌张数；
- 第五张同牌的非法情况；
- 公开弃牌/副露的可见张数；
- 清一色/碰碰胡/发财番数。

建议只做两件事：

1. 抽一个“从 `GameView` 恢复分析输入”的适配层，保证联网/回放不读隐藏信息；
2. 在 `evaluateHand()` 的输出上增加“逐家风险”，而不是重写向听。

### 6.3 和牌/听牌概率：优先解析，Monte Carlo 作为补充

助手的 Monte Carlo 可以借鉴，但建议分两层：

**第一层：快速解析（默认）**

对“下一张/未来 k 张至少摸到一张有效牌”使用超几何分布：

```text
P(至少一张) = 1 − C(未知牌总数 − 有效牌数, k) / C(未知牌总数, k)
```

这比 20,000 次模拟快得多，适合每手实时刷新。

**第二层：Monte Carlo（可选）**

只在玩家展开“未来 3 巡/5 巡”时运行：

- 未知牌池 = 4 份普通牌 − 自己手牌 − 所有弃牌 − 所有副露；
- 发财按 4 张计入未知池，摸到后走补牌；
- 对手每巡消耗未知牌；
- 自己摸牌后用“向听最小 + 进张最大”的轻量策略弃牌；
- 默认 2,000 次（UI）/20,000 次（离线报告）；
- 固定 seed，结果可复现；
- 用 `requestIdleCallback` 或 Web Worker，避免阻塞牌桌。

**报嘴规则必须单独处理**：

- 未报嘴且 `mouthRequired` 时，点炮胡不合法，模拟只能计自摸；
- 报嘴后锁定听口，模拟不能换听；
- 报嘴本身是一个合法动作，教练应在“可报嘴且收益为正”时提示，而不是只看向听。

### 6.4 风险模型：先做“可解释的粗估”，不要做“伪精确概率”

建议第一版只输出三档：`低 / 中 / 高`，附证据。等积累足够本地牌局后，再用实际点炮率校准区间。

校准方法：

1. 用 `records` 重放本地对局；
2. 对每次人类/AI 弃牌，记录当时的风险特征与实际是否点炮；
3. 按风险分数分桶，统计每桶的点炮率；
4. 用等渗回归或简单分位数重新切阈值；
5. 只有样本量足够时才显示百分比区间。

这比直接抄助手的 1%–30% 区间更可靠。

## 8. 验收标准

### 隐私

- 教练只接收 `GameView`，不接收 `GameState`；
- 修改对手暗手或牌山顺序，建议结果不变；
- 不读取 `lockedWaits`、对手 `concealedTiles`、`wall.tiles`；
- 联网对局默认不显示实时教练；如显示，只使用公开信息。

### 正确性

- 风险证据逐条可追溯；
- 现物、筋牌、幺九、副露、报嘴、巡目分别有单元测试；
- 报嘴/必须自摸的状态不会被当成普通听牌；
- 发财补牌不会进入手牌，也不会被算成普通进张；
- Monte Carlo 固定 seed 可复现。

### 性能

- 单次弃牌分析在普通 PC 上 < 16 ms；
- 2,000 次 Monte Carlo < 200 ms，或放入 Worker；
- 牌桌动画/出牌不被分析阻塞。

### 展示

- 教练面板不改变手牌坞高度；
- 不遮挡牌河、动作按钮、中央提示；
- 风险只显示“低/中/高”或明确标注“粗估”；
- 每条建议有“为什么”，不只有分数；
- 回放中明确区分“当时可见信息”和“事后结果”。

### 质量门禁

- `npm run quality` 通过；
- 新增测试覆盖风险、隐私、回放、UI 布局；
- AI A/B 报告包含胜率、点炮率、平均向听、平均进张，不只看“最优弃牌率”。

## 9. 不采纳项与风险

### 明确不采纳

1. **YOLO/OpenCV 读屏**：我们是自有牌桌，状态权威；引入模型只会增加错误和依赖。
2. **牌墙 OCR**：引擎直接知道 `wallRemaining`，OCR 是多余环节。
3. **Tkinter 悬浮窗**：与 React 牌桌的信息架构冲突；只借鉴卡片层级。
4. **七对子/十三幺/花牌/风牌**：不是本项目规则；照搬会产生错误听牌。
5. **助手的 42 类模型权重**：README 明确说不要公开分发，模型授权未确认；不复制、不打包。
6. **固定比例牌河识别**：对窗口比例和皮肤敏感，不适合作为产品依赖。

### 主要风险

| 风险           | 说明                        | 缓解                             |
| -------------- | --------------------------- | -------------------------------- |
| 风险模型未校准 | 助手区间本身未经牌谱校准    | 先只显示三档；用本地牌局分桶校准 |
| 规则差异       | 无风牌、无花牌、有报嘴/发财 | 重新实现，不直接移植             |
| 性能           | Monte Carlo 可能阻塞 UI     | 解析优先 + Worker/缓存           |
| 公平性         | 联网实时教练可能被视为外挂  | 本地/回放默认开放；联网默认关闭  |
| 过度承诺       | “点炮概率”容易被当成精确值  | 文案写“粗估/启发式”，给证据      |
| 代码来源       | 只有打包产物，无源码/测试   | 只借鉴方法，不复制代码           |

## 10. 最终建议

**建议做，但只做“分析层”，不做“读屏层”。**

最小可行版本：

1. `src/advice.ts`：从 `GameView` 计算逐家风险 + 每张弃牌的向听/进张/风险；
2. `CoachPanel`：在右栏展示首选 + 2 备选 + 原因，默认只在本地/回放开启；
3. `review.ts`：回放时对比“建议 vs 实际”，给出平均向听/进张损失和高风险弃牌次数；
4. 用真实本地牌局验证后，再决定是否把风险权重加进标准/进阶 AI。

这套方案能直接提升本项目的学习价值和 AI 可解释性，同时不破坏现有规则、联网隐私和 UI 结构。助手项目最值得学的是“把建议拆成可验证的证据”，而不是“用摄像头看别人的牌桌”。
